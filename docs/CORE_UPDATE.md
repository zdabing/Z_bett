# 一键更新 Mihomo 核心（2026-10-27）

源码已加入正式 LuCI 资源页。下述隔离测试形成于源码实现阶段，正式构建状态以 Release / Actions 为准；尚未安装到生产路由器或执行生产核心更新、启停。本地测试不能替代目标固件的原生 ucode、procd、DNS 和转发验收。

## 使用入口

在“资源 → Mihomo 核心”查看当前版本、最新稳定版、设备架构和可回退版本。

- **检查更新**：只查询版本，不切换核心。
- **更新并重启 / 更新核心**：自动检查、下载并校验最新稳定版；服务正在运行时切换后重启，原来停止时保持停止。不必先点击检查更新。
- **恢复随包并重启 / 恢复随包核心**：首次独立更新后可恢复软件包自带核心。
- **回退并重启 / 回退上一版**：已有上一独立版本时切回它。回退同样先校验，失败不会强行启用不兼容文件。

命令行入口如下。`update` 和 `rollback` 会实际切换文件，运行中的服务需要重启。

```sh
bettbox core status
bettbox core check
bettbox core update
bettbox core rollback
```

更新来源是 [MetaCubeX/mihomo 官方稳定发布](https://github.com/MetaCubeX/mihomo/releases/latest)，通过 [GitHub Releases API](https://api.github.com/repos/MetaCubeX/mihomo/releases/latest) 读取架构对应文件和 SHA-256。仅接受精确匹配的官方 HTTPS 下载地址、稳定版标签及非空 SHA-256；不允许自定义下载地址、无校验降级、预发布或自动降级到更旧版本。GitHub 不可达、限流或未提供校验值时返回错误，旧核心继续使用。

支持 x86_64（amd64-compatible）、aarch64/arm64、armv7l、armv6l；其他架构明确显示暂不支持，不猜测 MIPS 字节序和浮点 ABI。依赖增加 `gzip`、`coreutils-sha256sum`，应随完整的核心脚本与 LuCI/RPC 更新一起安装。

## 下载、切换与恢复

1. 下载在旧核心继续运行时进行；检查磁盘空间、压缩文件大小与官方 SHA-256。
2. 限制解压大小，检查 ELF 位数、字节序和机器类型，执行 `-v` 核对版本，并记录解压后可执行文件的 SHA-256。
3. 通过 init 的 `core_switch` 持有 procd 锁。正在运行时先用旧核心生成并校验当前配置，再用新核心校验同一个运行文件；没有运行文件时使用最小 DIRECT 配置，只代表基础可执行性验证。
4. 只有上述检查通过后才恢复普通 DNS、撤销本项目外置规则并停止旧核心，原子切换核心选择链接，再按原运行状态启动。启停沿用 [就绪检查与网络恢复流程](SERVICE_LIFECYCLE.md)。
5. 新核心启动失败时尝试恢复旧选择和上一版记录、重启旧核心；本次操作仍报告失败。DNS 恢复或旧核心恢复本身也可能失败，页面会重新读取实际状态并显示错误，不能把“已尝试恢复”理解为保证回退成功。

不覆盖 `/usr/bin/mihomo`，软件包核心仍由包管理器维护。独立核心保存在 `/etc/bettbox/core/releases/<版本-架构-压缩文件SHA>/`；`current`、`previous` 是相对符号链接，`package` 表示使用 `/usr/bin/mihomo`。保留当前和上一选择，清理其他符合自有命名规则的版本目录中的已知文件。包升级可能替换随包核心，因此“恢复随包核心”恢复的是当时的软件包版本，不保证等于首次更新前的版本。

核心切换不修改订阅、脚本、DDNS 或端口转发配置。Bettbox 配置备份仍只包含 UCI、订阅、脚本、规则，**不含独立核心二进制和版本选择**；恢复配置不回退核心。整机 sysupgrade 是否保留独立核心取决于设备备份设置，本功能未为它添加固件备份项。

## 任务、权限与中断边界

更新/回退是写权限 RPC `core_update`，与页面启动、停止、应用配置共享单任务准入锁；直接 CLI 的下载更新/回退另有文件锁，关键切换段通过 procd 锁串行化。读权限的 `core_info/core_check` 不能执行切换，通用 `diagnostic_start` 不接受 `core/service` 类型。

更新任务立即返回任务 ID，后台外层限时 1200 秒，页面查询预算 1230 秒；检查更新的后台限时 160 秒。页面等待完成状态和退出码，任务受理不代表更新成功；超时也不等于操作取消。服务/核心任务不继承普通诊断的文件大小限制，避免截断核心、配置或 Geo 数据；仅截取输出尾部最多 1MB。

下载与校验阶段不停止旧核心。**切换仍需重启，经过核心的连接可能短暂中断。** TUN 自动路由由 Mihomo 管理，尚未实测 DDNS 端口转发到 NAS 的已有连接能否连续保持；不能承诺全程无感。选择链接各自原子替换，也不等于突然断电时具备完整事务恢复。

## 本地验证

- `test/core-update-test.js`：29 项正式更新脚本的受控执行。真实 gzip/SHA-256 fixture，覆盖四种架构、官方元数据、下载/解压/版本/ELF/空间/配置失败、无运行配置、锁冲突不清理他人文件、版本选择与回退；未下载或运行真实核心。
- `test/service-lifecycle-test.py`：22 项真实 init shell 的隔离执行，包括新核心校验先于停止、原来停止时保持停止、候选校验失败保留旧实例、选择写入失败和启动失败恢复。procd、DNS、核心进程均使用测试替身。
- `test/shell-regression-test.py`：27 项隔离 shell 回归，验证配置校验使用已选择的独立核心。
- `test/core-test.js`：40 项控制器/RPC 回归，覆盖任务预算、互斥、完成解锁和读写权限；`test/diagnostic-worker-test.js`：22 项 worker 调度/输出检查；`test/service-operation-test.js`：10 项共享页面任务等待与超时检查。
- `test/resources-core-test.cjs`：正式资源页、共享组件/CSS 与 Zen 主题，七种宽度、深色手机、异步完成、按钮禁用、随包恢复、校验失败与读取失败恢复、已停止/不支持架构状态。使用受控 RPC，不连接路由器。

ucode 用例在 Node 中适配内置函数执行，不能当作原生 ucode 解析或目标设备验证。测试方法见 [测试说明](../test/README.md)。
